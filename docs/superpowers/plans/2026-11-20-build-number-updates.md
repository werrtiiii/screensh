# 同版本构建号更新设计

## 用户能做什么

客户端正常显示 `1.5.9`，在版本详情与更新诊断中显示 `1.5.9 · 构建 2`。更新器先比较三段版本号，只有版本号相同时才比较递增整数构建号。例如 `1.5.9 · 构建 2` 可更新 `1.5.9 · 构建 1`，而 `1.5.9 · 构建 999` 不能替换已安装的 `1.6.0 · 构建 1`。

支持构建号的首版必须通过一个比旧客户端更高的正式版本发出，例如正常发布 `1.5.9 · 构建 1`。安装前的 `1.5.8` 仍只比较版本号。首次升级成功后，后续小修复可保持 `1.5.9`，增加构建号。仍须发布更新产物，用户无需为每次热修手动下载安装包。

## 发布、校验与比较

- 保留正式 GitHub Release 和 `latest.yml` 的旧协议。热修产物使用独立且唯一的发布标识，例如 `hotfix-1.5.9-b2`。热修发布不得占用旧更新器的正式最新版入口。
- 新客户端读取一个固定位置的热修索引，从官方来源获取版本号、构建号、不可变产物地址、大小与 SHA-512。若未来允许通过第三方镜像提供索引，应先增加可验证签名。缓存和下载以完整目标身份及摘要区分，不用覆盖旧文件的方式发布热修。
- 构建时生成一份固定的构建身份，打进客户端和更新清单。更新器只接受身份合法且严格大于已安装构建的目标。比较正式更新和热修时仍以最高完整身份为准，正式版本跨版本优先。索引缺失或暂时不可读时仍可查正式版本。
- 先上传不可变产物和校验清单，验证整套文件后再更新索引。避免先给客户端展示一个还下载不到的目标。需要撤销一个有问题的构建时，从索引撤下以停止新下载；已经安装的客户端通过更高的构建号修复。

## 差分和免安装

1. **优先差分。** 复用 `app/main/update-blocks.cjs` 的分块校验和 HTTP Range 下载。仍通过摘要匹配本机内容，下载缺失块并拼成完整目标树。源和目标的三段版本号相同并不影响分块算法。需要扩展的是清单里的构建身份、`Blocks.bin` 地址和缓存键。
2. **回退完整 ZIP。** 差分不可用时，下载同一目标构建的 `Update.zip`。下载完成后退出应用，由现有原生更新进程备份并覆盖程序文件，保留数据，等待新构建启动确认。它是完整免安装更新，不需要运行安装向导，但需要重启应用。
3. **完整安装包是修复入口。** 免安装应用失败时先回滚。如果提供完整安装包，只能回退到相同目标构建且已校验的 EXE。不能把 `构建 2` 的请求回退到正式发布中的 `构建 1` 安装包。旧正式版本的 EXE 流程继续使用现有协议。

## 实现顺序和验收

1. **定义身份和清单版本。** 给构建比较、构建号缺失及非法值、跨正式版本排序写测试。兼容旧清单和旧缓存。不通过 SemVer 的 `+build` 代替比较，因为构建元数据不改变 SemVer 排序。
2. **打包并发现同版本构建。** 在 `update-source.cjs`、`portable-updater.cjs` 及发布脚本中接入热修索引、完整身份和定址规则。验证旧客户端仍可走正式更新，新客户端可以从正式构建查到同版本热修、拒收等于或低于本地的构建。构建 1 和构建 2 的文件名或不可变 URL 必须区分。同一构建号不能重新指向另一份内容。
3. **原生应用与启动确认。** `pending-update.cjs`、`update-cleanup.cjs`、`update-installer.cjs`、`portable-confirm.cjs`、原生 `Updater.cs` 和安装包回滚逻辑内的收据、事务、安装目标及确认检查共同采用 `(version, build)`。最终确认必须来自目标构建，旧版相同 `version` 的确认不能通过。差分清单、完整 ZIP 内清单、运行版本详情均来自同一构建身份。成功启动后再清理收据，较新的待安装构建要保留。
4. **隔离 Windows 端到端测试。** 验证 `1.5.8 → 1.5.9 构建 1 → 1.5.9 构建 2`，分别跑分块复用、Range 失败后回退 ZIP、目标构建启动失败回滚、旧构建不可误确认、退出后恢复待安装构建和用户数据保留。随后验证构建 2 不会重复下载，`1.6.0 构建 1` 仍可正常升级。

首版不引入应用运行中的热替换，不重新设计分块协议的内容匹配，也不改变旧客户端的正式版入口。

## 发布操作

- 正式版把 `app/package.json` 的 `version` 和锁文件升级到新版本，`screenshBuild` 设为 `1`，沿用现有正式标签，例如 `1.5.9`。
- 同版本热修保持 `version` 和锁文件不变，递增 `screenshBuild`，例如 `2`。用 `hotfix-1.5.9-b2` 标签构建已提交的代码。发布工作流上传 `Update.json`、`Blocks.bin`、`Update.zip`，校验上传后的摘要，再更新 `hotfix-index` 预发布中的 `ScreenSh-1.5.9-hotfix.json`。
- 客户端直接从官方仓库读取索引，产物 URL 由版本号和构建号生成。差分失败回退到同一构建的 ZIP。这一版热修不发布 EXE，独立更新器无法启动时显示可重试的错误；正式版本仍可回退到完整 EXE。
- 不复用已发布过的热修标签。索引推进后，已在运行的旧构建要在下次检查时才会看到更新。
