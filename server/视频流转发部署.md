# 使用外部 MediaMTX 转发共享

ScreenSh 信令服务不再内置或管理 EasyTier、MediaMTX，不需要 TUN、NET_ADMIN 或 root 权限；Docker 构建只使用 Node.js 基础镜像。原有 `SCREENSH_RELAY_ENABLED`、`SCREENSH_RELAY_IP` 等托管进程环境变量不再生效。

房主可选择「通过 EasyTier 组网转发」或「直连服务器 WHIP / WHEP」。默认保留 EasyTier 方案，旧配置不变；两种方式都由外部 MediaMTX 接收一路推流并向观看者分发。

## 1. EasyTier 方案：独立运行媒体服务

房主自行在某台主机运行 EasyTier 和 MediaMTX，两者必须在同一主机；EasyTier 需要 TUN 虚拟地址。可以复用 NAS 原有 EasyTier 网络，不需要额外创建 ScreenSh 专用实例。MediaMTX 需在此虚拟 IP 上监听，且其 HTTP 认证回调能够访问 ScreenSh 信令服务。

模板为 `mediamtx.external.yml`，将其中的 `10.126.126.1` 换成实际 EasyTier 虚拟地址。`authHTTPAddress` 填写从 MediaMTX 主机可达的信令地址，后缀固定为 `/media-relay/auth`；同机 host 网络部署可使用 `http://127.0.0.1:31012/media-relay/auth`，不同主机使用可信局域网地址或 HTTPS 信令域名。反向代理需将此路径转发到同一信令服务。

MediaMTX 可自行安装或使用可选的独立 Compose 示例：

```sh
docker compose -f mediamtx.external.compose.yaml up -d
```

这不是 ScreenSh 服务的一部分，启动、停止和升级由房主管理。新版 MediaMTX 可设置 `MTX_MOQ=false` 关闭本功能不使用的 MoQ 服务。虚拟地址的 TCP 8889 用于 WHIP/WHEP，UDP/TCP 8189 用于媒体；不需要对公网开放。

### Linux UDP 缓冲与现有 NAS 配置

模板将 `udpReadBufferSize` 设为 8 MiB、`udpMaxPayloadSize` 设为 1200。Linux 宿主机的 `net.core.rmem_max` 也必须至少为 8388608，否则只修改 MediaMTX 配置不足以获得所需的接收缓冲。先检查，低于该值时再增加：

```sh
sysctl net.core.rmem_max
if [ "$(sysctl -n net.core.rmem_max)" -lt 8388608 ]; then
  sudo sysctl -w net.core.rmem_max=8388608
fi
```

上述修改在宿主机重启后可能失效；验证有效后，将不低于现有值的 `net.core.rmem_max` 写入宿主机的 sysctl 持久配置。host 网络容器使用宿主机网络设置。随后重启 MediaMTX，并重新开始共享。

现有 NAS 若使用 HTTP 18889、媒体 UDP 35686，可用 `mediamtx.nas-network-settings.yml` 中的同名键替换原配置对应项，保留端口。该文件只是配置片段，不可直接替代完整配置；不要重复添加 YAML 键。若此 MediaMTX 还供其他业务使用，改为只监听 EasyTier IP 前，应确认那些业务也能访问该 IP。

`webrtcIPsFromInterfaces: true` 会枚举包括 Docker 网桥在内的宿主机网卡；host 网络中出现 `172.*` 候选地址本身不能证明媒体经过 Docker bridge。限制监听地址和候选地址可减少不相关路径，不能据此保证解决丢包。仍丢包时需进一步检查 EasyTier 实际通道、宿主机 UDP 丢包计数和可用带宽。

## 2. 软件内配置

在「服务器设置」填写：

- 视频转发方式：选择「通过 EasyTier 组网转发」。
- EasyTier 网络名称：与外部节点的网络名称完全一致。
- EasyTier 网络密码：与外部节点的网络密钥完全一致，不是 ScreenSh 服务器连接密码。
- MediaMTX 节点虚拟 IP：例如 `10.126.126.1`，不是公网节点连接地址。
- MediaMTX HTTP 端口：默认 `8889`。

保存后，网络名称、密码在成员下次进入服务器时生效；不会强制重启正在使用的虚拟网络。客户端在通过服务器访问验证后取得参数，并通过 EasyTier DHCP 自动分配同网络地址，例如节点为 `10.126.126.1/24` 时客户端可获得 `10.126.126.2`。保留旧配置的服务器在首次保存前沿用原来的默认网络与地址分配方式。

修改 MediaMTX 地址或端口会结束软件中现有的转发共享，需要重新开始。软件显示「已配置」只表示配置完整，不代表服务器已经探测媒体节点；实际可达性和认证在推拉流时验证。

### 直连服务器 WHIP / WHEP

在「服务器设置 → 视频转发方式」选择「直连服务器 WHIP / WHEP」，填写 MediaMTX 的 HTTP/HTTPS 根地址，例如 `http://服务器IP:18889` 或 `https://video.example.com`。不填写 `/whip`、`/whep`、流名称、账号密码或查询参数；软件为每次共享分配路径并附加凭证。IPv6 地址使用方括号，例如 `http://[公网IPv6]:18889`。HTTPS 证书需被客户端信任。

这种方式的推流、拉流不经过 EasyTier，不要求 MediaMTX 与 EasyTier 节点同机或加入相同虚拟网络。客户端其他组网功能仍使用 EasyTier，网络名称和密码继续按原方式配置；客户端是否有 TUN 不影响此媒体链路。

`mediamtx.direct.yml` 是独立配置模板。替换其中 `webrtcAdditionalHosts` 为客户端可达的服务器 IP 或域名，按实际部署修改认证回调。示例需开放/映射 TCP 18889（HTTP 握手）、UDP 35686（媒体），若启用备用 ICE TCP 同时开放 TCP 35686。只代理 HTTP 地址不会转发媒体 UDP/TCP；反向代理 HTTPS 时也要保留 WHIP/WHEP 的 POST、PATCH、DELETE、Location 和 CORS 响应头。保持 MediaMTX 的 HTTP 认证配置，不能直接使用匿名发布/读取的默认配置。

官方连接说明：[MediaMTX WebRTC connectivity](https://mediamtx.org/docs/features/webrtc-specific-features)。

切换方式或修改任一种转发端点后，软件结束现有转发共享并使旧凭证失效，需要重新开始共享。客户端和信令服务需一起更新，房主的选择保存在服务端配置中。

## 3. 使用转发

房主开启「支持外部视频转发」。共享者在共享设置勾选「使用服务器转发」后开始共享，软件将视频上传至已配置的 MediaMTX；观看者及共享者的自预览从该节点拉流。转发模式下共享者本地不启动 MediaMTX，内置采集与外部 OBS 均支持。EasyTier 方案下无 TUN 客户端使用内置 TCP/UDP 端口转发；直连方案直接使用原生 WebRTC/ICE 连接。

未勾选转发仍使用原来的本地 MediaMTX 直接共享链路。聊天、成员管理、凭证签发继续走信令服务，语音保持原有链路。

关闭软件中的支持开关只会停止软件使用该节点、撤销新会话凭证，不会停止房主独立运行的 EasyTier 或 MediaMTX。

## 4. 认证与边界

请按模板启用 MediaMTX 的 HTTP 认证，否则 MediaMTX 默认配置可能不校验软件签发的凭证。每路流使用随机路径；推流、观看凭证绑定成员、频道及操作，建立会话时检查有效期。未授权用户不能通过信令接口获取网络密码或媒体凭证。

离开频道、停止共享及关闭转发后，客户端主动关闭媒体连接，信令服务拒绝后续认证。由于信令服务不再控制外部 MediaMTX 管理 API，无法强制踢掉故意保留的已建立媒体会话；需要强制终止时由房主在外部 MediaMTX 管理。视频经媒体节点解密再转发，不是端到端加密。

服务器不转码，共享者上传一路，MediaMTX 下行约为视频码率乘以观看人数。所有参与者需要安装支持自定义组网参数的新版客户端。

## 5. 从专用实例版本迁移

保持现有数据卷及 `compose.yaml` 的节点、端口设置，上传新版程序文件与 Dockerfile，仅使用主配置重建：

```sh
cd /opt/screensh-server
docker compose -f compose.yaml up -d --build --force-recreate
```

不要再传入旧的 `compose.relay.yaml`。旧覆盖文件中的 root、NET_ADMIN、TUN 挂载可以删除；即使遗留旧环境变量，新程序也不会启动专用实例。原来的 NAS EasyTier 容器保持运行。完成软件内参数保存后，成员退出并重新进入服务器。
